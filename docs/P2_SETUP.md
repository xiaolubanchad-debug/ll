# P2 配置版本、任务和每日缓存

版本 1.2.0。中台新增配置容器、不可变版本及下载批次；Agent 0.3.0 新增 SQLite 任务记录、待回传队列和真实 Chromium 下载。P2 只执行 DOWNLOAD_ONLY。FULL 可保存，开始时明确拒绝；不安装 APK、不打开或注册产品账户。

## 更新顺序

1. 备份 PostgreSQL、主密钥、发布密钥和节点数据。更新中台源码并安装锁定依赖，执行 `npm run db:generate`、`npm run db:migrate`、`npm run build`，重启 API 和部署 Worker。新增迁移保留 P0/P1 数据并扩充节点占用槽。
2. 从干净的已提交源码执行 `npm run release:agent`，在中台登记新的签名清单。此发布声明 DOWNLOAD_V1，包含 Agent 0.3.0 和专用出口规则安装器；旧 P1 发布仍可登记，但不能领取下载任务。
3. 选择空闲的 EC2 执行节点部署新版本。身份目录仍按部署隔离，任务及缓存固定保存在 `/var/lib/apk-platform/execution`，升级不清空。Node.js 24 是必需条件，SQLite 使用其内置模块。

生产安装仍沿用 P1 的 Ubuntu/KVM 和固定 Android 工具链前置检查；本阶段没有另建不带 Android 的部署变体。旧 Agent 继续心跳，但页面提示需升级，服务端也会拒绝向其创建 P2 批次。

## 配置和开始

在“配置校验”页面填写 URL、XPath 和落地页规则，选择 DOWNLOAD_ONLY，并移除不用的代理引用。新建配置容器，再“保存草稿为新版本”。保存需登录及 CSRF，服务端执行相同校验，并通过 If-Match 阻止旧编辑覆盖；保存后可载入历史版本编辑，另存为新版本。

在“测试任务”选择在线、空闲且支持下载的节点，选择配置及具体版本，点击“开始下载”。发布版本固定为该节点当前安装版本。页面显示排队、领取、下载阶段、包名、缓存日期、摘要、失败原因和执行事件。保存新配置不会影响运行中的批次。一次开始创建有限批次；没有定时任务或无限循环。

界面暂用分页结果轮询展示，不提供执行日志的任意文本转发。待确认的请求重试保留原幂等键；刷新整个浏览器后应先查看已有批次，再明确决定是否新建。

## 下载行为

每个批次发现一次源页面目标；同一 pid 和 href 的轮播副本合并，无 pid 时保留位置。每个入口重新定位并实际点击；下载监听先于点击建立，支持直接附件、新窗口落地页和同页跳转。精确 host 的落地规则优先于 `*`，点击次数与下载重试有上限；空目标、超限、非 APK 和失效链接会返回失败。

`download.maxApkBytes` 可选，默认 256 MiB，范围 1 KiB–512 MiB。APK 验证包括 ZIP 条目路径、重复文件、CRC、解压大小和二进制 AndroidManifest 包名，记录静态版本、原生 ABI、大小与 SHA256。未验证 APK 签名、实际安装兼容性或产品后台；FILE_VALIDATION 结果不代表注册成功。

缓存按 nodeId、Asia/Shanghai 的下载开始日和入口 targetKey 区分。URL query 保留，fragment 不参与入口键。相同节点同日复用已校验 APK，命中仍复核完整性；文件损坏重新下载，跨日重新下载。日期在每个目标进入下载阶段时固定，跨午夜结束不改变归属。源页面发现仍随手动批次进行，不把整个网站访问缓存一天。

文件先进入本批次临时目录，成功后原子改名并写入 SQLite 缓存元数据。文件名由摘要产生，忽略网站提供的路径。默认清理超过 7 天且无活动引用的缓存；未完成任务引用保留。节点缓存不上传中台，普通接口不返回服务器绝对路径。

## 停止和故障恢复

P2 Agent 每 5 秒心跳，旧 P1 Agent 保持 15 秒；离线阈值仍为 45 秒。执行租约 120 秒、接收确认 30 秒。Agent 先持久化 delivery，再确认接收并核对配置摘要；每个外部动作前检查本地执行权。

排队任务停止可立即取消。已领取任务显示“停止待确认”，浏览器退出、临时文件清理完成后才上传安全停止回执；有失败或不能确认清理时保持隔离。未收到回执不能当作已停止。

Agent 重启后先读取持久任务、清理属于记录中专用目录的浏览器并向中台核验，不重新执行旧 delivery。Linux 清理核对进程所属用户和完整专用 profile 参数，不按程序名或裸 PID 杀进程；Windows 仅供开发，不能声称通过该生产恢复步骤。

租约失效、接收超时或重启导致的批次进入 NEEDS_REVIEW。先恢复节点服务、确认清理并等到新的空闲心跳，再在任务详情中人工核验解除占用。核验原因和管理员身份保存，原批次保持 NEEDS_REVIEW。新任务另建，可通过 API 的 supersedesRunId 关联原记录。迟到事件可留作证据，但不能释放新批次的槽。

## 网络和宿主机规则

浏览器与 APK 直接访问外网，不使用配置中的业务 HTTP 代理。节点本地出口代理逐连接检查全部 DNS 地址，阻止私网、loopback、link-local、metadata 和保留地址，并固定连接到已核验的 IP。浏览器取消 loopback 的默认代理豁免，禁用 QUIC 和非代理 WebRTC；每个批次使用专用 profile，不能共享登录状态。

用户已授权额外宿主机限制，仅对 apk-runner UID 生效，范围见 [授权记录](P2_EGRESS_REVIEW.md)。新服务启动前安装独立 nftables 表：允许本机通信和已配置中台的 HTTPS 端点，限制该 UID 的私网出口。其他账户、入站 SSH 和系统默认策略保持。白名单文件由 root 所有，执行账户不可写。中台私网地址变更或系统 DNS 不是本机解析时需重新核对规则；不能关闭指纹或网络检查来绕过失败。

本次开发未连接真实 EC2。规则生成、Linux 语法和本地浏览器防护的测试，不等于已经在实例上生效；上线还需核对 nftables 权限、DNS、HTTPS 及该执行用户是否专用。

## 验证

```sh
npm run lint
npm run typecheck
npm run check:contracts
npm audit --omit=dev --audit-level=high
npm test
```

测试使用真实 PostgreSQL 17.6、Node SQLite、Chromium 和自有本地 HTTP 站点；通过代码注入精确测试端点，不向管理配置提供内网放行开关。覆盖三种下载路径、轮播去重、版本与摘要固定、幂等与占用、完整缓存/损坏/跨日、APK 结构、停止回执、失效租约、乱序与重复事件、节点越权、重启不重跑、私网重定向，以及配置管理页面。

Linux CI 额外检查 Playbook、特殊密码原文、专用浏览器进程清理，以及 `nft --check`（只检查，不应用）规则语法。测试归档是运行时生成的结构化 APK 样本，不宣称可安装或有产品后台。所有缓存、数据库文件、测试包及截图留在忽略 Git 的临时目录。
