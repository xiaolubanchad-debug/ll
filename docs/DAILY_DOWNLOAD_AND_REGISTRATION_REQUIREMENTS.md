# 每日下载与注册配额需求增量

需求版本：1.5.0，记录日期：2026 年 10 月 28 日。状态：用户已确认以下业务规则，每日调度及注册配额尚未实现或部署。本文件是下一次开发的需求依据，不表示 Agent 0.4.x 已支持每日调度、成功配额或 App UA 控制；发布前还须补齐 Schema、状态转换与正反例。

## 已确认流程

每天北京时间 00:05（Asia/Shanghai）触发一次下载流程。访问中台配置的网站 URL，根据 XPath 获取全部符合条件的图标，依次点击。正常情况下每个入口当天只触发一次，注册循环不重新点击入口或下载 APK。

所有模拟使用移动端屏幕：网页、落地页和下载按手机浏览器布局及触屏执行；安装、启动和注册通过 Android 手机模拟器屏幕及原生控件执行。网页手机模式见 [1.4.1 契约](MOBILE_SCREEN_CONTRACT.md)，这不等于 App 设备身份或 UA 已变化。

下载必须覆盖三种情况：

1. 点击图标直接开始下载 APK。
2. 点击图标出现新 URL 的落地页，再按落地页规则点击下载。
3. 点击图标出现新 URL 的落地页，页面打开后自动开始下载，无需再次点击下载按钮。

新窗口和同页导航均需处理。下载监听必须先于来源点击及落地页导航建立；已经捕获下载时不再额外点击下载按钮。自动下载与人工下载按钮可能同时存在，需要专门验证不会过早点击造成重复请求。

当天的新 APK 下载并校验完成后，清理前一天的 APK 缓存，使用新包自动注册。清理仅限本系统拥有的缓存；仍被执行任务引用的旧包必须等任务安全结束后再删除。新包下载失败不能冒充更新成功，也不能静默把旧包当作当天新包执行。

## 注册目标与上限

中台增加两个独立配置：

| 配置 | 用户确认的含义 |
| --- | --- |
| 成功目标 N | 同一注册批次中，所有 APK 合计成功注册 N 个账户；不是每个 APK 分别 N 个 |
| 总尝试上限 M | 同一批次允许的注册尝试总数，防止失败后无限执行 |

成功数达到 N 后结束；尝试数达到 M 但成功数不足 N 时结束并如实报告未达目标。需要运行时校验正整数及 M ≥ N，避免无效或无限任务。注册页面展示累计成功、尝试、明确失败及未知结果，不能只显示执行轮次。

注册可反复复用当天已下载并校验的 APK，无需随每轮注册重新下载。每轮使用新生成的测试账户和独立模拟器数据环境，并轮换设备配置、重新建立代理连接。

失败后的新账户执行属于新的尝试，必须受 M 限制；同一次已提交注册仍禁止自动重发。提交结果 UNKNOWN 时暂停核验、保留账户与执行记录，不重复提交，也不靠新建批次绕过原未知结果。成功配额、尝试扣减和人工核验须幂等持久化，重复回执不能重复计数。

## 模拟信息的实际生效要求

用户要求每次注册前使用新的模拟信息，包括设备型号、请求 UA 和代理。实现必须区分请求的测试配置与实际观测：

- 新建 AVD 或改名不证明 App 收到了不同型号，也不等于新的真实手机。
- 网页浏览器 UA 不能替代 APK 请求 UA；普通 HTTP 代理不能直接改写任意 HTTPS App 请求头。要保证 App 实际上报的型号、UA 变化，需要对应 APK 支持测试配置入口或进行产品适配与验证。
- 重新连接轮询住宅代理不保证每个注册请求出口都不同；IP 探测只能证明探测当次的出口。不能把新连接或凭据引用当作新 IP 的证据。

未验证的字段继续按 P3 的实际证据表达，不能在界面或结果中伪称已变化。对需要保证变化的流程，能力未确认时应明确报告前置条件不足，而不是无证据地开始注册或标记成功。

## 实现前仍需收敛的规则

成功目标按单个注册批次计算已确认。每日新包就绪时如何创建下一批、前一批跨日未完成时如何协调、多个 APK 的尝试分配顺序，还需在实施契约中明确。用户不确定 APK 是否有型号/UA 测试入口，要求先检查代表 APK；静态分析发现的字段或方法引用只能作为线索，不能代替实际生效验证。调度与执行仍必须遵循数据库独占槽、幂等、租约和节点回执；不得与运行中的部署或注册并发清理文件。

当前代码已有直接下载、落地页点击及页面下载事件监听；Agent 0.4.1 的正式回归覆盖自有手机页面上的直接下载、新窗口及同页触控下载、新窗口立即自动下载、同页延迟自动下载，分别核对一次 APK 请求。移动端专用点击区域必须配置实际控件定位，不能只依赖“下载”文字。自动下载与备用按钮同时存在的去重仍需进一步细化。当前没有每日 00:05 调度，也没有 N/M 配额配置，不能据此标记为已完成。
