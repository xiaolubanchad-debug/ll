# 1.17 数量与每日额度

服务器页点“配置”：

1. 网站来源里填写“每日下载入口上限”，这是 XPath 匹配图标的数量保护，范围 1–1000，与 APP 重复打开次数无关。复制旧配置会保留旧值。
2. 每台最少/最多安装可超过 10，最多填写 1000。实际每台只抽取当天不同包名、且兼容当前系统的 APK；同台不重复。最少数量大于兼容包数时需下调，最多数量较大时自动按兼容包数缩小。
3. 每日额度默认自动估算，展示耗时依据、样本范围、25% 余量、已用和剩余。可选手动额度并点击“应用服务器额度”；这不会开始任务。改变配置的每台最少数量会更新估算建议。
4. 完成轮数 N 和总尝试上限 M 仍是本任务目标，需 N≤M，并受服务器当天剩余额度约束。8640 是 24 小时每次仅停留 10 秒的绝对保护边界，不是实际性能承诺；实际还包含准备、安装、代理与清理。
5. 保存后回服务器行点击开始。若上次因 TARGET_LIMIT 失败，先核对下载入口上限，点击开始后明确确认重新下载，才会使用新规则重访网站。失败历史保留。

当天首次新策略执行计划冻结额度。手动提高影响后续计划；降低和恢复自动次日生效。所有任务共享已开始次数，停止、归档、换配置不能清零。23:55 停止新增，只有清理回执确认后才显示空闲。

需要签名 Agent 0.14.0 和 EXECUTION_CAPACITY_V1 能力。旧 Agent 继续旧额度和不可变快照。保留单模拟器、每 APP 前台停留 10 秒、代理和设备清理，不增加并行。

本地验证：250 项契约检查、lint、全工作区 typecheck、正式 build 通过。P0–P3/浏览器回归分段执行；旧固定 800 的断言调整后重测通过。新增 PostgreSQL/Chromium 检查覆盖共享额度、自动估算、手动设置、冻结、鉴权、版本锁、幂等、37 包兼容裁剪、2000 次计划、无重复调度和大计划流式响应边界。原生 Java 客户端没有变更，本机缺少 JDK 的该项网络测试仍标记跳过，不把此项视作通过。

真实签名发布、中台升级、EC2 升级与 APK 实测单独核验；自有小批次不能代替全天或第三方产品吞吐验收。
